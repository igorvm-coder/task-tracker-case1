#Техническое задание
MVP «Трекер задач с автоматической отчётностью»
##1. Цель проекта
Разработать простое веб-приложение для небольшой команды до 5 человек, позволяющее создавать и отслеживать поручения, назначать исполнителей, контролировать сроки и просматривать сводную статистику по задачам.
Основная цель — исключить потерю поручений и обеспечить руководителю быстрый доступ к информации о состоянии работ.
##2. Состав MVP
В первую версию входят:
•	Авторизация по email и паролю.
•	Управление задачами: создание, просмотр, редактирование.
•	Назначение исполнителя из списка пользователей.
•	Изменение статуса задачи.
•	Автоматическое определение просроченных задач.
•	Табличный интерфейс с фильтрами.
•	Сводный отчёт по задачам и исполнителям.
•	Хранение данных в базе данных.
Не входят в MVP: канбан-доска, уведомления, экспорт в Excel/PDF, комментарии, приоритеты, вложения, сложные роли, Telegram-бот и интеграции со сторонними сервисами.
##3. Пользователи и доступ
Предусмотрено до 5 пользователей.
Каждый пользователь входит в систему по email и паролю. Неавторизованный пользователь не должен иметь доступа к списку задач и отчётам.
После успешного входа пользователь попадает на главную страницу со списком задач и сводной статистикой.
Важное правило доступа: до начала разработки необходимо согласовать, видят ли все участники общие задачи команды или каждый пользователь видит только назначенные ему задачи. Для командного трекера рекомендуется общий список задач для всех авторизованных участников, если конфиденциальность поручений не является требованием.
##4. Структура задачи
Поле	Тип	Обязательное	Правило
ID	Число или UUID	Да	Генерируется автоматически
Название	Строка	Да	Не может быть пустым
Описание	Текст	Да	Не может быть пустым
Исполнитель	Ссылка на пользователя	Да	Выбирается из списка
Дедлайн	Дата	Да	Указывается при создании
Статус	Перечисление	Да	По умолчанию «Новая»
Дата создания	Дата и время	Да	Заполняется автоматически
Приоритеты, теги, вложения и комментарии не реализуются.
##5. Статусы и бизнес-логика
Допустимые статусы:
1.	«Новая» — задача создана, но работа ещё не начата.
2.	«В работе» — исполнитель выполняет задачу.
3.	«Выполнена» — работа завершена.
Пользователь может изменить статус задачи через элемент управления в таблице или на странице редактирования.
Отдельный статус «Просрочена» не создаётся. Просрочка вычисляется автоматически:
Просрочена = текущая дата > дедлайн И статус != «Выполнена»
Просроченные задачи подсвечиваются красным цветом. Выполненная задача не считается просроченной, даже если её дедлайн прошёл.
Расчёт производится по календарной дате в установленном часовом поясе приложения. Задача с дедлайном сегодня не считается просроченной до наступления следующего календарного дня.
##6. Главный экран
Главный экран содержит два блока.
###6.1. Таблица задач
Столбцы:
•	Название.
•	Исполнитель.
•	Дедлайн.
•	Статус.
Дополнительные требования:
•	Фильтр по статусу.
•	Фильтр по исполнителю.
•	Красная подсветка просроченных задач.
•	Возможность создать задачу.
•	Возможность открыть задачу для редактирования.
•	Возможность изменить статус.
Таблица отображает задачи согласно согласованным правилам доступа. При отсутствии задач выводится понятное сообщение.
###6.2. Сводная статистика
Над таблицей или на отдельной вкладке отображаются четыре показателя:
•	Всего задач — общее число задач с учётом выбранных правил отображения.
•	В работе — количество задач со статусом «В работе».
•	Выполнено — количество задач со статусом «Выполнена».
•	Просрочено — количество невыполненных задач с истёкшим дедлайном.
Также выводится разбивка по исполнителям:
Исполнитель	Всего задач	Выполнено
Сотрудник 1	Количество	Количество
Сотрудник 2	Количество	Количество
Сводка пересчитывается при загрузке страницы и после создания задачи, изменения её данных или статуса. При изменении фильтров поведение статистики должно быть единообразным: рекомендуется рассчитывать её по всем доступным задачам, независимо от фильтров таблицы.
##7. Создание и редактирование задачи
Форма содержит:
•	Поле «Название».
•	Поле «Описание».
•	Выпадающий список «Исполнитель».
•	Поле выбора даты «Дедлайн».
•	Поле «Статус» при редактировании существующей задачи.
Система должна проверять заполнение обязательных полей и не сохранять некорректную задачу.
После успешного сохранения пользователь возвращается к списку задач, а статистика обновляется.
Если список исполнителей пуст, система должна предложить добавить пользователя либо сообщить, что назначение невозможно.
##8. Требования к авторизации и безопасности
•	Вход по email и паролю.
•	Пароли хранятся только в виде безопасного хеша.
•	Доступ к защищённым страницам разрешён только после авторизации.
•	Проверка доступа выполняется на сервере, а не только средствами интерфейса.
•	Секреты и пароли базы данных не размещаются в публичном клиентском коде.
•	Выход из системы завершает пользовательскую сессию.
Механизм регистрации пользователей и добавления новых участников необходимо согласовать отдельно. Для минимальной версии допустимо предусмотреть создание учётных записей администратором или вручную через готовые средства платформы.
##9. Требования к хранению данных
Необходимо хранить пользователей и задачи в базе данных.
Минимальные сущности:
User
•	id;
•	email;
•	password_hash;
•	created_at.
Task
•	id;
•	title;
•	description;
•	assignee_id;
•	deadline;
•	status;
•	created_at.
Связь: один пользователь может быть исполнителем нескольких задач. У каждой задачи один исполнитель.
После перезагрузки страницы созданные задачи и их статусы должны сохраняться.
##10. Нефункциональные требования
•	Приложение работает в современном браузере на компьютере.
•	Интерфейс простой, без сложных анимаций.
•	Основные действия доступны без лишних переходов.
•	Отчёт формируется на основе сохранённых данных.
•	Система показывает понятные сообщения об ошибках.
•	Внешние интеграции и платные сервисы не требуются, если они не входят в уже имеющуюся инфраструктуру заказчика.
##11. Критерии приёмки
Работа считается выполненной, если проверены следующие сценарии:
1.	Пользователь может войти с корректными учётными данными.
2.	Неавторизованный пользователь не может открыть список задач.
3.	Можно создать задачу со всеми обязательными полями.
4.	Новая задача сохраняется в базе данных.
5.	Можно назначить задачу одному из пользователей.
6.	Можно изменить статус задачи с «Новая» на «В работе», а затем на «Выполнена».
7.	Фильтр по статусу корректно отбирает задачи.
8.	Фильтр по исполнителю корректно отбирает задачи.
9.	Задача с дедлайном в прошлом и незавершённым статусом подсвечивается красным.
10.	Выполненная задача не подсвечивается как просроченная.
11.	Сводные показатели и статистика исполнителей соответствуют данным в базе.
12.	После перезагрузки страницы данные сохраняются.
##12. План разработки
###Этап 1
•	Подготовка проекта и базы данных.
•	Авторизация.
•	Создание и отображение задач.
•	Назначение исполнителя и изменение статуса.
###Этап 2
•	Фильтры и подсветка просрочки.
•	Сводный отчёт.
•	Проверка критериев приёмки.
•	Исправление основных ошибок и передача результата.
##13. Ограничения и допущения
Предполагается максимально простая реализация с использованием готовых инструментов и минимального количества сторонних зависимостей.
Хостинг – бесплатный. Домен, дальнейшая техническая поддержка и дополнительные функции, не перечисленные в настоящем ТЗ – не гарантируются
Выбор конкретного стека технологий определяется исполнителем. Приоритет — рабочий MVP, а не сложная архитектура или расширяемость
